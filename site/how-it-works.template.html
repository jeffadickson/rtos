How NexRT schedules work, how to write an application, and where drivers meet the CPU.

This is a host-side developer guide generated from the checked-in examples and assembly. RISCue firmware cross-builds; hardware execution, other CPU ports and board qualification remain separate work.

What the kernel does

Static application threads→Scheduler + optional IPC→CPU port→Board hardware

Before scheduling, main registers permanent thread control blocks and stacks. start() seals the registry, creates private idle state, configures the timer and dispatches. At each scheduling boundary the highest ready priority wins. Larger priority numbers take precedence; equal priorities rotate when requested. A sleeping or blocked thread permits other work to run.

The kernel has no general heap, runtime thread creation or stack growth. Optional queues copy bounded values, mutexes serialize device transactions with priority inheritance, events represent readiness, and semaphores count tokens. These single-hart mechanisms do not provide SMP locking or DMA coherency.

The measured nano image is {{IMAGE}} bytes of code/initialized data and {{RAM}} bytes of committed RISCue RAM, including the 4096-byte boot reserve. This guide and web services are excluded from that minimal image.

static rtos::Queue<Sample, 4> samples;
// Producer: check full explicitly.
auto sent = samples.send({1, 42});
// Consumer thread: timeout is ticks; failure leaves sample unchanged.
Sample sample{};

Enable RTOS_SYNC for these services; enable RTOS_LOGGING for bounded queued printf. Keep pointee lifetime explicit if a message contains a pointer. Use one permanent output thread and one logger for a shared console.

Write a small driver

A driver owns register access, clock/reset setup, operation deadlines and recovery. The kernel supplies scheduling and ownership. Construct one permanent driver per physical device and share that object among its client threads.

  1. Obtain the hardware register map, access widths, endianness, reset values and timing contract.
  2. Keep MMIO in one board-facing class. volatile preserves accesses; it does not make a multi-register operation atomic or supply a bus fence.
  3. Wrap the whole command/data/status transaction with DeviceTransactions, not each individual register.
  4. Bound ownership waits and hardware completion separately. A stalled AXI load requires interconnect timeout/recovery; a software timeout cannot rescue a non-returning bus transaction.
  5. Return explicit results and retain fault state until hardware is known safe. Never silently reuse an owner-dead device.
class Device {
    rtos::DeviceTransactions transaction_;
public:
    rtos::Result execute(uint32_t command) {
        return transaction_.transact(100, [&]() {
            // Board code: write command, wait to a bounded deadline,
            // read status, and acknowledge completion.
            // Replace this placeholder with your verified register protocol.
            (void)command;
            return rtos::Result::invalid;
        });
    }
};
static Device shared_device;

The placeholder deliberately does not claim to perform I/O. Thread clients call the same instance. The acquisition timeout covers the mutex, not callback duration. ISR code must only use documented nonblocking APIs after the port provides verified dispatch/acknowledgement. The present RISCue port enables its machine timer only; a completion event alone does not install a peripheral interrupt handler.

For a first integration, prefer bounded polling and a single owning worker. DMA is a later adapter with explicit buffer ownership, address/cache policy, completion and cancellation/quiescence. PCIe/SpaceVPX additionally needs versioned peer messages and fault/window isolation. No generic cache flush or bus address is guessed.

How preemption crosses assembly

Reset disables interrupts, establishes sp/gp, clears BSS and calls main. There is no constructor runner or ROM-to-RAM data copy. A loader must place initialized data correctly.

A trap may interrupt any live register. The vector saves every integer register and machine continuation state before calling C++. The scheduler returns a different saved-frame pointer; assembly changes stacks only after the C++ call unwinds, restores the selected frame and executes mret.

Frame bytesState
0Unused x0 slot
4..124x1..x31; original sp at byte 8, restored last
128mepc; ECALL advances by four, timer keeps the interrupted PC
132mstatus; MIE remains clear during restoration
136..143Alignment padding; frame total is 144 bytes

The frame constructor uses the same layout. Initial status 0x1880 selects machine mode with MPIE set and MIE clear. First mret enables interrupts after restore. Runtime traps save the 144-byte frame on the interrupted thread's stack and then switch sp to the dedicated linker-reserved trap stack via mscratch (_stack_top) before calling rtos_trap, isolating kernel C++ frames from application stacks.

Hardware scheduler & banked RISCue-MT contexts

16-Thread TMR Arbiter (1 cycle)→Parallel 64-bit Deadline Comparators (Tickless)→8-Bank TMR Register File (~5-cycle switch)

On FPGA soft cores such as RISCue, NexRT can offload scheduling decisions and context storage directly into synthesizable SystemVerilog without compromising the static-only contract:

  • NexRT-HWSched v1 (rtl/nexrt_hw_sched.sv, rtl/nexrt_hw_sched_axi.sv): a 16-thread AXI4-Lite peripheral at 0x1001_0000 providing 1-cycle combinational priority + starvation-free per-priority round-robin arbitration, 16 parallel 64-bit hardware deadline comparators against mtime (eliminating periodic tick interrupts when idle), 4 hardware peripheral IRQ-to-thread 1-cycle wake routes, hardware residency/dispatch/WCET watchdog counters, and Triple-Modular Redundancy (TMR_ENABLE=1) with automatic 1-cycle scrubbing.
  • RISCue-MT Banked Register File (rtl/riscue_banked_rf.sv, ports/riscue/context_banked.S): 8 TMR-protected hardware register banks (x1..x31, mepc, mstatus) indexed directly by NexRT-HWSched's active_tid. Pinned real-time threads skip all 72 AXI register transfers (~5-cycle switch vs. ~200+ cycles over AXI), while threads with tid >= 8 assert spill_required and fall back transparently to standard RAM frames.

Formal verification & compile-time thread safety

Testing alone catches only observed interleavings. NexRT combines type-level prevention in zero-overhead C++17 with machine-checked SMT formal proofs in Dafny (Z3) and closes the Proof-to-Silicon loop by executing the Z3-verified Dafny code directly against Verilated SystemVerilog RTL.

Dafny / Z3 SMT Proofs (formal/*.dfy)→dafny translate cs Verified C# Oracle→Lockstep Check vs. Verilated RTL (nexrt_hw_sched.sv)→Static-Audited RV32IM Firmware (rtos_safe.hpp)

Layer 1: Compile-time defect elimination (include/rtos_safe.hpp)

Whole classes of concurrency defects become compile errors with zero heap, zero RTTI, and zero runtime constructors (validated on RV32IM in examples/flagship_stateforge.cpp):

  • Deadlock impossibility (OrderedLock<T, Level> + LockToken<HeldLevel>): acquiring a lock requires a token satisfying static_assert(Level > PrevLevel). Out-of-order lock cycles cannot compile, and protected state T is private inside the wrapper so unsynchronized data races cannot compile either.
  • Zero priority inversion & single blocking (CeilingResource<T, CeilingPriority>): Immediate Priority Ceiling Protocol (IPCP/SRP) raises effective_priority to the resource ceiling on entry and rejects callers whose base priority exceeds the ceiling.
  • Stack/TCB binding (StaticTask<StackBytes, Priority>): bundles one non-copyable Thread and aligned Stack so stack aliasing or size mismatches cannot occur.
  • ISR vs. thread capability separation (TypedChannel<T, Capacity>): separates ThreadSender, ThreadReceiver, and nonblocking IsrSender handles so blocking sends from ISR context fail to compile.

Layer 2: Machine-checked Dafny + Z3 formal proofs (formal/*.dfy)

Why keep Dafny on the host verification plane instead of compiling Dafny C++ into the bare-metal kernel? Dafny's experimental C++ backend emits DafnyRuntime.h, std::shared_ptr, and heap-allocated sequences—violating NexRT's -nostdlib and zero-heap ELF audit. Instead, Dafny proves the core algorithms for all inputs and compiles to a rock-solid .NET 10 C# executable oracle (tools/NexRT.FormalOracle) that verifies live arbitration traces from the Verilated hardware scheduler inside CTest (dafny_rtl_lockstep).

Port the CPU and the board separately

Tang Nano 9K is an FPGA board, so its selected soft core determines the interrupt ISA, timer and memory map. Classic MicroBlaze is a separate architecture from MicroBlaze V. Do not substitute RISC-V assembly for a classic MicroBlaze context switch.

A port needs an exact hardware design/export, compiler ABI, endianness, RAM, timer frequency/registers, interrupt routing, startup/vector policy and cache policy. Until these are checked, configuration status stays provisional/planned. Cross-build evidence does not establish board execution.

The Sphinx manual contains the detailed API, source reference, driver inventory, platform status and target qualification checklist.

Small uploaded diagnostics and QSPI boot

Planned: reserve one optional RAM slot and one permanent diagnostic worker at boot. Ground tools link an image for that exact slot and firmware/service ABI, retain ELF symbols for debugging, and upload a flat payload plus a checked manifest. The target needs bounded transfer, validation and activation, without an ELF parser or runtime symbol resolver. Slot and worker storage still count toward RAM; the minimal build has neither.

Replacement requires a stopped worker and no outstanding references or device operations. Uploaded native code shares kernel privilege; a qualified watchdog/reset path is needed for hung code. Cache and instruction-fetch synchronization must be supplied by the actual board port before activation.

QSPI can store boot and diagnostic images. Copying boot code into RAM does not reduce execution RAM; XIP can, when the FPGA controller supports memory-mapped instruction fetch. The current flat-RAM port has no QSPI/XIP driver or flash-to-RAM data initialization. See the Sphinx manual's Uploaded diagnostics and QSPI boot chapter for the full planned contract.

RTOS_BOOT_STACK_BYTES now makes the boot reserve explicit and configurable. Its default stays 4096 bytes; smaller values require startup call-chain and board validation. Runtime traps switch to this dedicated reserve via mscratch.

ARM simulation and verification

The Cortex-M3 QEMU port runs privileged threads on PSP and kernel handlers on a separate MSP stack. Hardware saves eight integer-frame words; assembly prefixes BASEPRI, EXC_RETURN and r4–r11. SVC handles blocking calls; SysTick preempts. This differs from the RISCue frame shown above.

The stress application uses nine worker/coordinator stacks, static queues and extra test state. Its memory use is not the minimal configuration measured at the top. Register and NZCV canaries, interrupted-PC witnesses, timer catch-up, rollover, ARMv7-M MPU stack-guard protection (arm-stress-mpu) and queue variants exercise real exception paths. Host models add repeatable IPC checks; optional ASan/UBSan and Valgrind inspect host C++.

The Sphinx manual contains the complete ARM assembly, stack layouts, driver contracts, libgloss explanation, build examples and evidence limitations. VORAGO, Zynq, classic MicroBlaze and a specific Tang Nano soft SoC still need their exact BSP and port work.
